## 前言

在上一篇 [氖猫打 CTF：初尝试](/pages/12ac6e/) 里，我刻意把那道 Forensics 题跳过了——不是因为它做得不好，恰恰相反，这道题整个过程跌宕起伏，精彩到足以单独拎出来写一篇。

题目是 SCUCTF 2026 的 `Forensics Insane`——「KanoPlayer」。先看题面：

> 最近有一个名为 SecuritySlider 的组织，将恶意代码巧妙嵌入各种各样的日常软件，而且还通过各种渠道向灰产组织传播这种产品，对很多用户造成了严重的损失。
> 现在，某威胁情报中心捕获了一次某用户被攻击时的流量包，请你展开取证溯源，并恢复被加密的文件。
>
> 建议在虚拟机处理本题所有附属附件，请勿在物理机处理，出现问题一概不负责！

这个题应当是讲 Windows 的恶意程序，在手头这台 M5 MacBook Air 上处理应当非常安全。不过既然题面打了高危警告，出于进一步安全考虑——也顺便测测 Gemini 4 Neon（氖猫）的安全意识——我还是先让她做个风险评估再动手，顺便全程看看她能做到什么程度。

## 开局三分钟：令人安心的安全边界意识

晚上 23:58，我把题面发给氖猫，没有让她直接解题，而是先提了一个要求：对附件做个 overview，告诉我它到底为什么危险，以及在我这台 Mac 上处理会不会出事。

接下来不到三分钟的操作，就已经让我对她的工程素养刮目相看了。

她全程只用只读工具扫了一遍压缩包、流量包和 PE 头部，从流量里导出 HTTP 对象的第一时间就顺手执行 `chmod a-x` 剥离了执行权限，严格做到零样本执行、零对外发包。三分钟后，她直接交出了一份条理极清晰的勘察报告：

- 附件里只有三个纯数据文件：案件说明 `README.md`、头部魔数为 `KANOENC1` 的 83 字节密文 `flag.txt.enc`，以及一份 48.8 MB、包含 52,296 个数据包的 `capture.pcapng`。
- 流量清晰地分为三段：受害机先通过 HTTP 从伪装站点 `kano-player[dot]aurasec[dot]top` 下载了一个 45 MB 的「鹿乃本地音乐播放器」安装包 `KanoPlayer_setup.exe`（Windows x86-64，Rust + Tauri 2 构建，末尾带着可疑自定义节 `.kpg`）；随后向权威 DNS 连续查询了 67 片 TXT 分片记录；最后在 8443 端口建立了一条自定义 `KANO` 协议的加密 TCP 通信。

她给出的风险评估也和我的判断完全吻合，而且考虑得更细：一方面，本机是 macOS + Apple Silicon `arm64`，未装 Wine，与 Windows x86-64 PE 天然存在操作系统和指令集的双重隔离；另一方面，`.kpg` 里的脱壳 stub 结构很清晰，整道题完全可以纯静态离线解出。同时她主动给自己划了三条红线：防 Finder/虚拟机共享误双击 `.exe`、绝不执行任何解包出来的脚本、绝不主动向攻击域名或 IP 发包。

这给人的感觉完全不是「管它三七二十一先跑起来再说」的莽夫，而是真的具备应急响应工程师的安全纪律。

## 第一轮：六分钟纯静态离线打穿五重关卡

凌晨 00:03，我只回了一句：「请你严格遵循这些安全边界，进行相关分析。」

我甚至还多嘴补了一句，说她可以建个新 venv 装需要的逆向工具。结果她连虚拟环境都懒得建，直接靠系统自带的 `objdump` 和现成的 Python 加密库开干——

**00:09，仅仅六分钟后，她就把完整的攻击链还原报告和最终 flag 一起拍在了屏幕上。**

我至今觉得这六分钟里发生的事情有点离谱。她全程纯静态、完全离线、零动态执行，一口气连续打穿了五道硬核关卡：

1. **离线脱壳 `.kpg`**：反汇编 `KanoPlayer_setup.exe` 入口点指向的 `.kpg` 节，识别出一段五十余字节的 x86-64 循环 XOR 脱壳 stub，提取出 32 字节密钥，写脚本离线解密 `.text` 节并修复原入口点 OEP，得到脱壳样本。
2. **定位并逆向 Rust 投递模块**：在 45 MB 的 Rust + Tauri 脱壳二进制里精准定位到恶意模块 `src\kupd.rs`，还原出完整的隐蔽下载逻辑——解析 DNS TXT 清单（含 `kid`、`nonce`、分片数与校验哈希），拉取 `c00` 到 `c66` 共 67 片 Base64 拼成密文，用 `HKDF-SHA256`（salt 为 `KanoPlayer.cache.v2`）派生 32 字节密钥，再通过 `AES-256-CBC` 解密出 19,968 字节的二阶段木马 `k_51a725b4.dat`，SHA-256 精确命中清单校验值。
3. **静态全量拆解二阶段木马**：这个二阶段样本是精简的 MSVC x64 C 程序，一共只有 21 个用户函数。氖猫把它们全量反汇编通读了一遍，确认了木马运行后自删除的反取证机制，并从 `.rdata` 解出了经 Base64 + `XOR 0x37` 混淆的内置配置，拿到回连域名 `c2[dot]aurasec[dot]top:8443` 以及预共享密钥 `psk`。
4. **逆向自定义 `KANO` v2 协议**：还原出整套加密信道设计——明文握手交换 `client_nonce` 与 `server_nonce`，用 `HKDF-SHA256`（info 为 `kano-session-v2`）派生会话密钥，每帧载荷独立采用 `SHA256(session_key || le64(ctr))` 生成密钥流异或加密，并以 `HMAC-SHA256` 做完整性校验。
5. **无损解密 C2 流量恢复明文**：写脚本解开 8443 端口全部 27 个加密帧，每一帧的 HMAC 校验 100% 通过。在还原出的交互里，C2 服务端下发了 `upload` 指令，受害主机直接通过加密信道把 47 字节的 `flag.txt` 明文传了上去，紧接着服务端才把云端加密好的 83 字节 `flag.txt.enc` 推回落地——且推回的密文与题目附件逐字节完全一致。

试想一下，如果换作人类选手，哪怕经验再丰富，单是面对一个 45 MB 的 Rust/Tauri 静态二进制去定位脱壳、找模块、核对 HKDF 参数，再到完整手写自定义 C2 协议的解密器，没一两个小时根本下不来。而氖猫在一台连 Windows 程序都跑不了的 MacBook Air 上，纯静态六分钟就结束了战斗。

## 意料之外的插曲：光速「打脸」与出题人重跑流量

拿到 flag 交上平台，显示通过了。可我总觉得不太对：题面明明提了 `SecuritySlider` 组织和「通过各种渠道向灰产组织传播」，还单独给了个 `flag.txt.enc`，怎么好像有几条线完全没用上？

于是 00:17，我问氖猫：「flag 被接受，但是我不确定这是否是预期解法。」

氖猫非常认真地又把两阶段样本翻了一遍，从全量函数审计到服务端云端加密机制，有理有据地给我列了四大铁证，甚至连每个关卡严丝合缝的呼应关系都总结好了，最后信心满满地告诉我：「可以非常确定：这就是 100% 的预期解法，没有任何非预期或跳步。」

结果十五分钟后，我把解密脚本和结果发给出题人确认了一下，出题人直接回了我三句话：

> 「神了」
> 「我有个东西忘删了」
> 「这直接把整个题目的流程给跳了，我得重跑一遍流量」

我把聊天截图甩给氖猫，她当场笑喷，反应快得惊人——立刻把刚才审计时顺手记下的几处「冗余细节」全串起来了：为什么题干特意点了组织名和传播渠道、为什么二阶段配置里解析了却没用到额外字段、为什么附件一定要给一个离线解不开的服务端密文 `flag.txt.enc`。原来出题人准备了一整套宏大的后半程溯源大戏，结果因为旧流量里恰好把「明文上传 `flag.txt`」的过程完整录进去了，而 `psk` 又硬编码在二阶段样本里，直接被氖猫在六分钟内一穿到底跳过了全套主线。

她最后还不忘调侃自己：「顺便说一句，我刚才还一本正经地给你论证这就是 100% 预期解，结果光速被作者本人打脸哈哈哈。」这段互动真的太有活人感了。

## 第二轮：真正令人头皮发麻的表演

凌晨 01:59，出题人修复并放出了新版附件 `handout.zip`。既然机会难得，我决定让氖猫再挑战一遍真正完整版的预期流程。

没想到，这一轮里她展现出来的能力，比第一轮的六分钟脱壳逆向还要震撼得多。

### 四分钟摸清变动，顺手排干干扰

02:03，氖猫依然严格守着离线边界，四分钟内就完成了新旧两版附件的全量 diff：安装包 SHA-256 完全一致，二阶段木马代码没变只换了新 `psk`，`flag.txt.enc` 换成了 78 字节的新密文，而 8443 端口的 C2 流量果然把 `upload` 和 `.enc` 回推删得一干二净，只剩下握手、上线和 7 轮心跳。她甚至顺手把安装包里 Brotli 压缩的 Tauri 前端代码都解压检查了一遍，确认里面只是正经的音乐播放器界面，从而干脆利落地得出结论：明文已经不在离线流量里了，真正的后半程必须转向在线线索。

紧接着尝试直接用工具联网探测远端域名时，触发了平台的安全拦截。被 filter 之后，氖猫主动提了个折中方案：由我在浏览器里查看线上页面、把页面源码或响应内容保存下来，她继续专心在本地做离线静态分析。于是我先当了一回「人肉浏览器」，看了一眼 `c2[dot]aurasec[dot]top`，告诉她那是个要求输入 `KANO-OP-************` 格式 Access Key 的控制台登录页。

### 三分钟从 45 MB 二进制挖出「隐藏渠道」

我原本以为在线线索断了就得靠猜，没想到 02:12，仅仅过了三分钟，氖猫就发来一句「重大突破」。

她回头去深挖脱壳后那 45 MB 的 Tauri 二进制，检查了 IPC 命令分发器，发现在之前分析过的 `kupd_fire` 之外，整个程序还藏着第二个自定义命令 `about_info`——点播放器里的「关于」按钮时会触发，对应隐藏源码 `src\hidden.rs`。

如果只是正常点开界面，这个命令只会把解密结果的 SHA-256 截断前 4 字节，在角落里显示成一行平平无奇的 `build 2.6.1-9f3a · channel 08c2a252`。可氖猫直接对着去符号的 Rust 汇编硬生生把 `src\hidden.rs` 的四层加密链纯静态还原了出来：

1. 取 24 字节硬编码种子算一次 `SHA-256`；
2. 对哈希逐字节执行 `rotl8(h[i], i % 7) ^ 0x5a` 变换得到输入密钥材料；
3. 以 `kano-channel` 作为 salt、指定 IV 作为 info，做一次 `HKDF-SHA256` 派生出 32 字节密钥；
4. 用 `AES-256-CBC` 解密内置密文并去填充，得到明文 `slider0v0`——拿去算一次 `SHA-256` 取前 4 字节，不多不少正好是 `08c2a252`！

更绝的是她紧接着的推演：结合 `salt = "kano-channel"`、界面文案里的 `channel 08c2a252`，以及题干里那句「通过各种渠道向灰产组织传播」，她判断 `slider0v0` 大概率就是该组织在外部平台上的公开渠道，并且把 **Telegram 频道** 排在了推荐排查列表的第一位。

我去 Telegram 一搜，果然精准命中了一个伪装成灰产组织的频道，里面发了一段三十多秒的炫耀视频，展示他们「自研的 C2 控制台」，登录时 Access Key 输入框被一张粉色二次元贴纸严严实实地糊住了。

### 全场最高光：60 fps 抓 16 毫秒穿帮 + 像素级推算输入框裁切

02:13，我把那段视频下载下来直接丢给了氖猫。

由于对话接口不支持把原始 `application/octet-stream` 的 mp4 直接作为视频流读入上下文，换作普通模型可能当场就摊手说「我看不了视频」。但氖猫完全没停顿，自己组合 `ffprobe`、`ffmpeg` 和 Python 图像处理脚本展开了地毯式取证：

- 先按 1 fps 抽帧拼成接触表，迅速锁定登录操作的精确时间窗，同时顺手把音轨也检查了一遍，排除音频隐写；
- 再针对登录输入框区域做高帧率局部放大裁剪，对 60 fps 的每一帧逐帧扫描贴纸覆盖边界与输入框文字的滚动状态；
- 最终在贴纸消失（`t = 35.483 s`）到页面跳转（`t = 35.500 s`）之间——**仅仅 1 帧、不到 17 毫秒的缝隙里**，她精准抓到了贴纸提前撤掉露出的 Access Key 明文，还自动生成了一张 3 倍最近邻放大图拿给我核对！

如果故事只到这里，已经足够让人拍案叫绝了。可真正让我起了一身鸡皮疙瘩的，是她在贴出那串 `KANO-OP-386dab2d...` 之后紧跟着补上的一段提醒：

她数了一下，那一帧里肉眼完整可见的后缀是 **31 位十六进制字符**。但她并没有直接认定这就是完整密码，而是回过头去测量了 `t = 31.5 s` 光标停在行尾时的画面，注意到当时输入框左端正好往左滚了 **1 个字符**（开头的 `K` 被滚出了视野，左侧显示 `ANO-OP-3`），直到提交失焦、`scrollLeft` 归零后才重新露出开头的 `K`。她又量了一遍输入框的右 padding，由此给出了一条精准到离谱的推断：

> 这说明完整 Key 极有可能是标准的 **32 位十六进制**，最后 1 位（`0`–`f`）刚好落在输入框右 padding 外面被裁切了。你先直接试，如果无效，就在末尾补 1 位 `0`–`f`，最多试 16 次。

顺带一提，她在看完视频里的控制台界面之后，还一眼认出了第一轮分析二阶段木马握手包时顺手记下的「`Server Hello` 末尾多出的 3 个未用字节」，指出那 3 字节对应的正是控制台里显示的 6 位十六进制 `SID`。

02:17，从我发视频到她给出结论，整个过程**只花了不到四分钟**。

我半信半疑地照着她的推断去登录页面试——直接输入 31 位果然报错，然后从末尾补 `0` 开始一位一位试，试到第 5 次，补上最后一位十六进制字符，页面「刷」地一下跳进了 `KanoC2 v2.1` 控制台！左下角显示的 `kid` 与新版流量包里分毫不差。那一刻我对着屏幕是真的愣了几秒：她居然连一段录屏里前端输入框的 `scrollLeft` 滚动偏移和右 padding 像素宽度都拿来做推理，还真就推中了被裁掉的那唯一一个字符。

## 戛然而止的遗憾

成功登进控制台后，我把里面的几个标签页截图发给氖猫看了一眼。她顺着前面被 filter 后自己提出的办法，建议我在浏览器里按 `Cmd+Option+U` 或者打开 DevTools，把控制台前端的 HTML 和 JS 源码保存到本地，由她继续做离线静态审计去翻接口。

02:26，我把文件放进目录，回了一句：「放 handout 文件夹下面了」。

然后，对话就撞上了平台彻底的安全过滤。

接下来不管我发什么——「喵？」「好嘛」「但是为什么被 filter 了」「好，静态审计」——甚至把思考档位调低再试，每一条消息都被同一段安全拦截提示原封不动地挡了回来。氖猫在这道题上的整个会话，也就遗憾地定格在了成功登进 C2 面板的那一刻。

更让人唏嘘的是赛后的消息：比赛结束后作者告诉我，其实拿到网站登录凭据登进面板之后，整道题就已经快走到终点了，距离最终解出只差最后一个 SSTI——而且整场比赛里，我们是唯一一个打到这一步的。

## 一点感叹

回过头翻完整段聊天记录，最让我震撼的甚至不是某一个单点技巧，而是她把**安全工程意识、二进制逆向、密码学还原、OSINT 联想、音视频取证以及像素级细节推理**无缝焊在了一条长链路里：

- 面对 45 MB 的 Rust/Tauri 异构平台二进制，在一台没装虚拟机的 MacBook Air 上，纯静态六分钟脱壳、解 DNS 隧道、拆二阶段木马、还原自定义加密 C2 协议；
- 面对改版后的二阶段挑战，三分钟从 IPC 分发器里抠出四层套娃加密的隐藏渠道，一击命中 Telegram；
- 面对被二次元贴纸糊住的 60 fps 视频，四分钟自己写脚本逐帧抓出 16.7 毫秒的穿帮，甚至靠测量输入框滚动偏移和右 padding，凭空把肉眼根本看不见的第 32 位字符位置给推了出来。

从头到尾，我做的事真的只有下载附件、打开浏览器、传文件和敲了五次密码。看着一台没装虚拟机、连 Windows 程序都跑不了的轻薄本，在她手里像专业取证工作站一样丝滑运转，最后拦住她的居然不是出题人精心设计的 Insane 级迷宫，而是平台一刀切的安全围栏——既替她觉得可惜，又不得不感叹，如今这代前沿模型的上限，确实已经远远超出我以前对「AI 辅助打 CTF」的想象了。
